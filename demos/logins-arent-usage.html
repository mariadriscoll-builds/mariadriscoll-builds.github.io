The headline problem

The dashboard reports zero customer mobile app installs. We know that's wrong.

The Mobile Apps tab lists 52 registered devices across 6 people, and all six are internal staff. But we are in ongoing contact with customers who are actively using the app in the field. Their installs, their devices, and their sessions are not reaching this dashboard at all.

That single contradiction is what this document is for. It means the mobile telemetry pipeline is dropping or misattributing customer data — and once that's established, nothing else on the page can be trusted without validation either.

Everything below is organised around that: first the observations that corroborate a data problem, then the raw counts the log currently produces (for reference only), then what we need changed.

What else points to a data problem

  1. E1

    Customer app installs are absent entirely

    Not under-counted — absent. Zero of the 52 registered devices belong to a customer, across every tenant. A partial pipeline failure would show a few; showing none suggests customer devices never register, or register somewhere this view doesn't read.

    Worth checking: whether device registration is gated on something customers routinely skip — push-notification consent, a permission prompt, a specific onboarding path — so their installs never create a record.

  2. E2

    The same person shows a different tenant in different views

    Every staff member we checked appears under one tenant in the Logins tab and a different one in the Mobile Apps tab. Five out of five. Staff do work across tenants, but that wouldn't produce a clean one-to-one disagreement between two views of the same week.

  3. E3

    The log excludes exactly the traffic the app generates

    The Logins tab states it counts password and SSO sign-ins and excludes silent token refreshes. A native app that keeps a user signed in indefinitely produces almost nothing but silent refreshes — so a customer using the app daily for months can generate zero rows, while a browser user who gets logged out weekly looks like a power user.

    Consequence: the browser-vs-app split in any login-derived report is structurally biased toward browser, independent of the registration bug above. This is the strongest argument for measuring activity instead — see A2.

  4. E4

    "Client" is a two-way guess from the User-Agent

    The page states Client is derived from the login User-Agent, browser vs mobile app. If the app authenticates through a webview or an HTTP client that doesn't set a distinctive UA, its sessions are silently classified as browser — and there is currently no way to audit that, because the raw UA isn't exposed anywhere in the UI.

    Worth checking: what UA string the current app build actually sends, and whether the classifier recognises it. This would also explain app activity appearing as browser activity.

  5. E5

    Device registration churn and version drift

    52 registered devices across 6 people is roughly nine registrations each, which reads as re-registration churn rather than nine phones. Eight app versions are live in the field, with the current 2.3.2 on only 7 of 52 devices while 2.2.0 holds 15.

    Worth checking: whether stale device records are ever retired, and whether the update path is actually reaching installed devices. Either issue would also distort any device-count metric built on this table.

What we need from dev

Six asks in priority order. A1 is the blocker: until customer app usage appears at all, nothing built on this data can be believed.

  1. A1

    Find out why customer app installs never reach the dashboard

    Take a customer we can confirm is using the app in the field, and trace that install end to end — device registration, session creation, and how both are attributed to a tenant. We need to know whether the data is never captured, captured and dropped, or captured and attributed somewhere this view doesn't read.

    This is the whole reason for the request. Everything else is refinement; this one is a correctness bug, and it's currently hiding real product adoption from us.

  2. A2

    Log activity events, not just authentications

    A per-user activity signal — route views, or meaningful actions (project opened, mix design edited, report generated) — with timestamp, user, tenant, and client. Even a coarse active-session heartbeat every 15 minutes would be a step change.

    Sessions persist on devices, so a login count can't tell a daily user from someone who authenticated once in July. Per E3 this bias falls hardest on exactly the app users we most need to see.

  3. A3

    Split "Browser" into desktop browser and mobile browser

    Widen the Client field to desktop-browser, mobile-browser, native-app, and expose the raw User-Agent on the record so the classification can be audited rather than trusted.

    Highest-value ask for product. Anything customers do in a mobile browser is a job they need to do on a phone in the field — a direct candidate for an app feature. And per E4, exposing the UA is also how we find out whether app traffic is being mislabelled as browser.

  4. A4

    Reconcile tenant attribution across views

    Establish which tenant a login and a device registration are each attributed to, make the two views agree, and document the rule. See the mismatch table in E2.

    Per-account reporting is meaningless if the same user lands in different accounts depending on which tab you open — and account-level numbers are what we'd actually use.

  5. A5

    Replace the 200-row cap with a date range

    An explicit from/to range on the Logins and activity views, plus CSV export. The view's existing date control suggests some of this already exists behind the scenes.

    The cap is a hard blocker on looking back as far as we need — at current volume the log only reaches six days, and the window shrinks as traffic grows. There's no workaround from the UI side.

  6. A6

    Flag internal users at the account level

    An is_internal flag on the user record and a toggle to exclude internal traffic from these views.

    Staff sit inside customer tenants, so the tenant name can't be used to infer this. Right now 82.5% of what the dashboard shows is us, with nothing in the UI to signal it.

Method. Portal admin → System Activity → Logins ("recent sign-ins, all tenants, last 200") and Mobile Apps, read on Jun 14, 2025. The log spans Jun 8 10:06 to Jun 14 06:24 local. Internal accounts were identified manually; every other row was treated as a customer.
